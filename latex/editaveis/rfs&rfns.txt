{Requisitos funcionais}

Os requisitos funcionais definem as ações e comportamentos esperados do sistema no escopo do MVP~1. A Tabela~\ref{tab:rf-borafut} apresenta os principais RFs derivados das \textit{user stories} dos épicos 1 a 6.


RF01 - O sistema deve permitir o cadastro de novos usuários por e-mail, solicitando pelo menos nome, apelido e e-mail, com posição em quadra como informação opcional.

RF02 - O sistema deve enviar um código de verificação para o e-mail informado no cadastro, para validação e ativação da conta.

RF03 - O sistema deve permitir que o usuário atualize seu e-mail, exigindo confirmação por meio de um novo código enviado para o endereço informado.

RF04 - O sistema deve permitir que o usuário faça login informando apenas o e-mail, recebendo um código temporário para autenticação (\textit{passwordless}).

RF05 - O sistema deve manter a sessão do usuário ativa após o login e permitir que ele encerre a sessão quando desejar.

RF06 - O sistema deve permitir que o usuário (registrado ou não) navegue em um mapa interativo, aproximando, afastando e movendo a visualização para explorar quadras na região.

RF07 - O sistema deve permitir que o usuário (registrado ou não) centralize o mapa na sua localização atual, utilizando geolocalização do dispositivo.

RF08 - O sistema deve permitir que o usuário (registrado ou não) pesquise quadras pelo nome.

RF09 - O sistema deve permitir a aplicação de filtros no mapa (por exemplo, tipo de quadra, favoritas, quadras com jogos em andamento ou agendados) e destacar visualmente esses resultados.

RF10 - O sistema deve permitir que o usuário visualize, no perfil de uma quadra, informações básicas como endereço, tipo de piso, iluminação e se é pública ou privada.

RF11 - O sistema deve permitir que o usuário visualize avaliações e a nota média de uma quadra, quando existirem.

RF12 - O sistema deve permitir que o usuário registrado avalie uma quadra de forma geral.

RF13 - O sistema deve exibir no perfil da quadra a quantidade de futs realizados recentemente e a lista de futs agendados naquele local.

RF14 - O sistema deve permitir que o usuário registrado marque uma quadra como favorita e acesse posteriormente a lista de quadras favoritas.

RF15 - O sistema deve permitir que o usuário abra o endereço da quadra diretamente em um aplicativo de mapas instalado no dispositivo, para traçar rota até o local.

RF16 - O sistema deve permitir que o usuário registrado visualize os detalhes de um fut (evento), incluindo quadra, data, horário, modalidade, vagas, regras básicas e organizador.

RF17 - O sistema deve exibir, para cada fut, o número de participantes confirmados, o número de vagas disponíveis e a lista de jogadores confirmados.

RF18 - O sistema deve permitir que o usuário registrado confirme e cancele sua presença em um fut.

RF19 - O sistema deve permitir que o usuário compartilhe um fut por meio de link ou mecanismo nativo de compartilhamento do dispositivo.

RF20 - O sistema deve permitir que um usuário registrado crie um fut em uma quadra existente, definindo data, horário, modalidade, número máximo de jogadores, descrição e regras básicas.

RF21 - O sistema deve permitir que o organizador edite as informações de um fut que ele criou.

RF22 - O sistema deve permitir que o organizador exclua um fut que ele criou, removendo-o da listagem de eventos disponíveis.

RF23 - O sistema deve permitir que o usuário registrado realize \textit{check-in} de chegada à quadra, para registrar sua presença física no fut.

RF24 - O sistema deve permitir que o organizador adicione manualmente à lista de jogadores participantes que não possuem conta no aplicativo.

RF25 - O sistema deve enviar um e-mail para o potencial usuário adicionado manualmente, informando sua participação no fut e convidando-o a criar uma conta.

RF26 - O sistema deve exibir uma fila de jogadores associados ao fut, indicando a ordem de participação nas próximas partidas.

RF27 - O sistema deve gerar automaticamente times com base na fila de jogadores (por exemplo, ordem de confirmação ou chegada), distribuindo-os entre os times da próxima partida.

RF28 - O sistema deve permitir que o organizador registre o início e o término de uma partida, bem como o placar de gols de cada time.

RF29 - O sistema deve, ao término de uma partida, atualizar automaticamente a fila de jogadores de acordo com as regras definidas (por exemplo, “perdeu, saiu; ganhou, ficou”).

RF30 - O sistema deve apresentar ao usuário registrado estatísticas básicas de sua participação em futs (como número de partidas jogadas e vitórias/derrotas).

RF31 - O sistema deve permitir que o organizador visualize um resumo estatístico básico do fut (como número de partidas realizadas e de jogadores diferentes que participaram).

RF32 - O sistema deve permitir que o usuário registrado altere seu apelido exibido no aplicativo.

RF33 - O sistema deve permitir que o usuário registrado selecione ou envie uma imagem para utilizar como avatar em seu perfil.

\subsection{Requisitos não funcionais}

Os requisitos não funcionais estabelecem propriedades de qualidade, restrições técnicas e padrões que o sistema deve seguir no MVP~1. A Tabela~\ref{tab:rnf-borafut} apresenta os principais RNFs definidos para o \textit{BORAFUT}.

RNF01 - O aplicativo deve ser multiplataforma, funcionando em dispositivos Android e iOS compatíveis com a versão mínima definida do sistema operacional.

RNF02 - O backend deve responder às principais operações (login, listagem de quadras, criação e atualização de futs) em até 3 segundos, em condições normais de rede.

RNF03 - A interface deve seguir princípios de usabilidade e heurísticas de Nielsen, priorizando clareza, consistência e simplicidade de navegação.

RNF04 - A autenticação deve seguir o modelo \textit{passwordless}, utilizando códigos temporários enviados por e-mail, sem armazenamento de senhas no sistema.

RNF05 - Os dados devem ser armazenados em um banco de dados relacional \textit{PostgreSQL} hospedado em provedor de nuvem.

RNF06 - A comunicação entre o aplicativo e o backend deve ocorrer por meio de uma API \textit{REST} sobre o protocolo \textit{HTTPS}.

RNF07 - O sistema deve implementar práticas básicas de segurança, incluindo proteção de endpoints, uso de tokens de autenticação e não armazenamento de códigos temporários em texto puro.

RNF08 - O aplicativo deve estar em conformidade com a LGPD, incluindo coleta de consentimento, apresentação de política de privacidade e restrição de uso a pessoas com 16 anos ou mais.

RNF09 - O código do projeto deve seguir padrões de estilo definidos (por exemplo, ESLint e Prettier), mantendo consistência e facilitando a manutenção.

RNF10 - O backend deve registrar logs básicos de operação e erros, suficientes para diagnóstico de problemas em ambiente de produção.

RNF11 - O aplicativo deve apresentar funcionamento adequado em redes móveis 4G e Wi-Fi, com comportamento resiliente a variações temporárias de conexão (por exemplo, mensagens de erro claras em caso de falha).
